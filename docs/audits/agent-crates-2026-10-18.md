# Crate research for agent reliability and monitoring — 18 October 2026

Companion to the [agent reporting audit](agent-reporting-2026-10-18.md). Recommendations below are engineering judgments based on the agent at baseline commit `21d1413`, upstream documentation/source, and crates.io release/dependency metadata. This research added no dependencies. The companion audit records subsequent reliability fixes using existing dependencies; the candidates here have not been benchmarked or validated on the four release targets.

The best approach is to keep `sysinfo`, expose capabilities the agent already has, and replace selected custom parsers and CLI integrations. Reporting scheduling, metric scope, failure isolation and updater transactions require application-level policies; adding a crate alone does not correct them.

## Recommended shortlist

| Decision | Crate / version researched | What it replaces or adds | Main qualification |
| --- | --- | --- | --- |
| Use more of the existing dependency; evaluate upgrade | `sysinfo` installed **0.37.2**, current **0.39.6** | Existing APIs already provide uptime, boot time, available memory, per-core CPU, network packet/error counters, MTU, addresses and filesystem read-only state. | Keep source/scope explicit and refresh only needed data. An upgrade does not fix the custom cgroup override. |
| Adopt for Linux parsing | `procfs-core` **0.18.0**, or `procfs` **0.18.0** | Custom `/proc/stat`, diskstats, meminfo, mounts, VM and pressure parsers; structured CPU user/system/iowait/steal counters. | Prefer `procfs-core` when keeping controlled I/O and parsing fixtures on macOS; use `procfs` for its Linux file-reading helpers. |
| Adopt for container collection | `bollard` **0.21.1** | `docker ps`, `docker stats`, human-readable percentages/byte units and port formatting. | Keep explicit socket selection, API negotiation, deadlines, bounded concurrency and protocol validation. |
| Adopt when replacing service CLI collection | `zbus` **6.0.0**, or `systemd-zbus` **5.3.2** with its compatible zbus 5 dependency | `systemctl list-units` text parsing; typed unit properties, service exits/restarts and change notifications. | Linux-only collector. Version 6 was released two days before this audit; generated bindings currently depend on version 5, so choose one compatible stack. |
| Adopt for a Rust updater's version logic | `semver` **1.0.28** | Three inconsistent version comparisons in Rust, TypeScript and shell. | Standardize release syntax, handle old `v1`-style inputs deliberately, and compare precedence without treating build metadata as a new release. |
| Useful additions when implementing the related feature | `nix` **0.31.3**; `sd-notify` **0.5.0** | Safe filesystem statistics for inodes/flags; systemd readiness, status and watchdog notifications. | A safe syscall can still block. A watchdog must detect internal loss of progress, not restart the agent during every server outage. |

The project release builder uses Rust 1.96. Declared minimum versions are compatibility clues, not proof that the complete resolved dependency graph builds on 1.96; an absent minimum is unknown.

## Use the existing libraries first

I checked the **installed 0.37.2 source**, rather than assuming every missing metric requires another library. `System::uptime`, `boot_time`, `available_memory`, `cgroup_limits`, `NetworkData::total_packets_*`, `total_errors_on_*`, `mtu`, `ip_networks`, and `Disk::is_read_only` already exist. Extend the protocol and consumers to expose them. The cgroup memory helper still needs a deliberately selected host/guest scope. [Upstream sysinfo documentation](https://docs.rs/sysinfo/0.39.6/sysinfo/), [network API](https://docs.rs/sysinfo/0.39.6/sysinfo/struct.NetworkData.html).

Evaluate **0.39.6** separately: its changelog includes Linux network-number fixes, parent-cgroup memory-limit handling, network refresh improvements, a new interface operational-state API, and earlier macOS memory-accuracy improvements. Its declared Rust minimum is 1.95, below this project's release toolchain. Retain minimum macOS compatibility tests and evaluate only needed features. [Upstream changelog](https://github.com/GuillaumeGomez/sysinfo/blob/master/CHANGELOG.md).

For scheduler repair, existing Tokio already has `Interval` and `MissedTickBehavior::Skip`, bounded channels, timeouts and task primitives. Use an independent sampler and delivery task with at most one active collection; skipped ticks alone cannot make an awaited collection branch independently pollable. `tokio-util` is already used by the server and offers cancellation/task tracking if useful for the refactor. Existing workspace `tracing` can provide structured collection/transport diagnostics. No new scheduling framework or metrics exporter is necessary for the current reporting protocol. [Tokio timing](https://docs.rs/tokio/1.53.3/tokio/time/enum.MissedTickBehavior.html), [TaskTracker](https://docs.rs/tokio-util/0.7.20/tokio_util/task/struct.TaskTracker.html).

## Replace parsing and subprocess work selectively

**`procfs-core` / `procfs`: strong fit.** Replace `parse_diskstats`, `parse_meminfo_cache`, `parse_root_mount`, and route/membership parsing where supported. Capture diskstats once for both aggregate and per-device values. Add typed CPU breakdown and pressure/VM metrics. `procfs-core` contains portable parsing/data structures, so Linux input fixtures can run in the native macOS test suite. The full crate provides Linux reads and optional fields for kernel-dependent data. Continue to own monotonic delta timing, counter reset handling, byte/list limits and unavailable states. ZFS kstats are a separate format and are not automatically covered. [procfs API](https://docs.rs/procfs/0.18.0/procfs/), [procfs-core parsing API](https://docs.rs/procfs-core/0.18.0/procfs_core/).

**`bollard`: strong fit.** Read typed container lists, inspection state, health and numeric stats from the local daemon. This removes CLI process startup and the agent's percentage/unit string parsers. For local sockets, upstream documents `default-features = false, features = ["pipe"]`; avoid pulling in remote transports/build tooling without a requirement. Negotiate the daemon API and handle older hosts: some summary health fields only appear in newer APIs. Numeric counters still require correct CPU/rate calculations, and typed ports still need bounded conversion to H.O.P.E's protocol. Socket access must remain an explicit installation choice. [Bollard docs and feature options](https://docs.rs/bollard/0.21.1/bollard/), [health API compatibility](https://docs.rs/bollard/0.21.1/bollard/service/struct.ContainerSummaryHealth.html).

**`zbus` / `systemd-zbus`: strong fit for service monitoring.** Keep one system-bus connection, query watched units individually so a missing unit remains visible, and read structured service result, main exit status and restart count. Subscribe to relevant changes instead of enumerating every service on every sample. A generated proxy for the small used interface over zbus is another option. Avoid loading the session bus accidentally. Missing systemd, bus denial or an unknown property must degrade the service collector only. `systemd-zbus 5.3.2` declares `zbus ^5.7.0`; do not combine its proxy types with zbus 6. [zbus runtime/features](https://docs.rs/zbus/6.0.0/zbus/), [ServiceProxy properties](https://docs.rs/systemd-zbus/5.3.2/systemd_zbus/struct.ServiceProxy.html), [published dependency metadata](https://crates.io/api/v1/crates/systemd-zbus/5.3.2/dependencies).

## Cgroups: evaluate a library, but fix the measurement boundary first

Both **`libcgroups 0.7.0`** from Youki and **`cgroups-rs 0.5.1`** from Kata Containers are credible alternatives to the agent's custom hierarchy/controller parsing. Youki documents v1/v2/hybrid managers and CPU usage/throttling, memory, PID and I/O statistics. These could support effective resource limits and throttling without expanding the custom parser. Neither library can decide whether this product intends to monitor a host, LXC guest or the agent's own service. [Youki's library documentation](https://youki-dev.github.io/youki/developer/libcgroups.html), [cgroups-rs API](https://docs.rs/cgroups-rs/0.5.1/cgroups_rs/).

Prototype **one**, not both, after defining that boundary. `libcgroups` has broader runtime-oriented dependencies including OCI types, `pathrs`, `procfs` and nix; disable its systemd feature unless required, and do not enable the optional BPF device-controller feature for read-only monitoring. `cgroups-rs` currently has an unconditional zbus dependency and another nix version, so it is not automatically the lightweight choice. Check the selected read-only paths, error behavior and musl build before adoption. A narrow adapter around a tested library is preferable when the actual API removes more complexity than it adds. [Youki feature manifest](https://github.com/youki-dev/youki/blob/v0.7.0/crates/libcgroups/Cargo.toml), [Kata dependency metadata](https://crates.io/api/v1/crates/cgroups-rs/0.5.1/dependencies).

## Updater research: useful components, no drop-in repair

**`semver` is worth using.** The Rust helper ignores prereleases/build suffixes, the shell strips them, and the UI implements its own numeric comparison. A release `1.2.3-rc.1` can therefore fail to advance to `1.2.3`. Use a canonical release version and one shared precedence policy; `Version::cmp_precedence` deliberately ignores build metadata. Normalize or explicitly reject legacy non-SemVer versions. Keep the shell bootstrap small and move shared policy into a signed Rust helper if the updater is rewritten. [semver Version API](https://docs.rs/semver/1.0.28/semver/struct.Version.html).

**`self_update 1.3.1` was researched and is not my recommended immediate replacement.** It supports backends, verification hooks and executable replacement, but H.O.P.E needs root-owned service/config transactions, pinned trust, accepted-report confirmation, interrupted recovery and updater migration. Those product requirements remain. Its daemon defaults are interactive unless configured otherwise; its signature feature uses a different scheme from the current RSA manifest. Adoption in a privileged helper would require an explicit design, not calling self-update from the unprivileged agent. [Upstream self_update documentation](https://docs.rs/self_update/1.3.1/self_update/).

**`tough 0.24.0` is a later option if release metadata is redesigned.** It is a TUF repository client with verified metadata/target loading and expiration enforcement. It could replace part of the bespoke update-distribution trust protocol, but requires publishing TUF metadata and bootstrapping/migrating trust; it does not stop/start services or roll back an agent that cannot report. Keep it out of the initial scheduler/update-recovery repair. [Tough documentation](https://docs.rs/tough/0.24.0/tough/).

For updater locking, Rust's standard `File::try_lock` is already used in `config.rs`. A Rust helper can reuse process-owned locking without adding `fs2`/`fs4`. A dropped file lock and a recoverable transaction journal are separate requirements.

## Alternatives not selected

- **`heim`, `psutil`, `systemstat`:** investigated as broad collection alternatives. A second general-purpose system collector would overlap heavily with the existing sysinfo integration. Start with the verified APIs above; compare an alternative only against a specific unsupported metric/platform and benchmark it. The latest stable heim release in the queried metadata is from 2020; this is a reason for additional maintenance review, not proof that all upstream work stopped. [Heim](https://docs.rs/heim/), [psutil](https://docs.rs/psutil/), [systemstat](https://docs.rs/systemstat/).
- **`hdd 0.10.3`:** not a general solution for SMART/NVMe coverage. Its stable release dates to 2020 and its own roadmap still names broader device support, including NVMe. Prefer a bounded, low-frequency `smartctl -j` integration using existing serde JSON parsing and explicit access to devices. The existing `command()` helper rejects nonzero exits; SMART integration needs tool-specific interpretation so a health warning is not discarded as “collector unavailable.” [hdd upstream scope](https://github.com/vthriller/hdd-rs), [smartctl JSON option in upstream source](https://github.com/mirror/smartmontools/blob/master/smartctl.cpp).
- **A metrics exporter / retry framework:** not necessary merely to send the self-health fields in the audit. Typed diagnostic fields and existing tracing/reqwest/Tokio cover that requirement. A retry library cannot decide whether a 403 is authoritative revocation or whether a sample is safe to drop.

## Adoption order and validation

1. Fix scheduling and source/scope policy with existing Tokio/sysinfo. Expose the available uptime, memory, network and read-only metrics.
2. Add `procfs-core`/`procfs` and `bollard` behind collector adapters. Keep invalid optional telemetry from blocking core reports. Test real Docker API versions and daemon-unavailable behavior.
3. Replace systemctl parsing with a compatible zbus stack; evaluate one cgroup library against nested systemd/LXC fixtures.
4. Add `semver` and filesystem/watchdog helpers with their associated changes. Preserve the current credential and pinned-key boundaries.
5. Compare binary size, idle RSS, average CPU, collection latency and outage behavior before/after. Re-run Linux ARM64/x86_64 musl and macOS ARM64/x86_64 builds, minimum macOS checks, and real systemd/launchd rollback tests. Source/metadata research alone does not establish these costs or platform guarantees.
