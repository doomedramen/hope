# Reliability implementation — 20 October 2026

Scope: Linux x86_64 only, as confirmed by the project owner. This ledger follows the [baseline review](reliability-review-2026-10-20.md). It records local implementation and verification; it does not certify a deployed release.

## Implemented

| Review finding | Change | Regression evidence |
| --- | --- | --- |
| 1 — Stored records and derived device views share a persistence path | `StoredHost` is a distinct validated storage type. Mutation paths load stored records; projected views cannot be passed to `save_host`. Source overrides live in their own table. Identity decisions run through one transactional reconciler, with unique indexes enforcing confirmed associations. Migration 15 repairs legacy persisted projections while preserving history and aliases. | Compile-fail boundary test; network refresh, settings/report, migration and association constraint tests. Existing source migration/merge and scanner tests still pass. |
| 2 — Unlink immediately relinks | Unlink records a durable manual rejection; explicit reset permits automatic reconciliation again. Reads no longer make identity decisions. | Unlink followed by reads, a report, and explicit reset; database pointer assertions before projection. |
| 3 — Artifact overlays lose checksum entries | Publishing downloads into separate staging directories, validates the expected server artifact and generates the final manifest from the final server/agent artifacts. Scope follows the concurrent Linux x86_64 restriction. | Release assembly tests reject absent, corrupt and duplicate manifest entries and a missing agent bundle. |
| 4 — Failed server upgrades destroy the working installation | Host and Proxmox upgrades use one activation helper with a writer lock, stopped-service verification, private SQLite/file backups, durable journal, rollback and an orphaned-activation startup guard. Health must come from the unit's process ID. The old source checkout stays intact; agent signing and the Proxmox version marker advance only after activation succeeds. | Real SQLite/filesystem fault injection with fake systemd/HTTP covers migration rollback, WAL contents, wrong-process health, failed first install, stop failure, signals, retry, concurrent installers, custom configuration and the Proxmox binary layout. Host integration tests verify preservation of the signed agent release after failed activation. |
| 5 — Transient notification failures lose messages | Migration 16 adds a bounded durable outbox. Condition transitions and messages commit together; failed HTTP requests retain messages with persisted retry deadlines. Endpoint and credentials are snapshotted together. | Failed publish, restart, retry, success and recovery ordering; queue-capacity deferral; settings cancellation. |
| 6 — Notification HTTP blocks discovery | Independent condition evaluator and delivery worker; four concurrent deliveries, per-condition ordering, bounded HTTP deadline and cancellation-aware shutdown. Network I/O holds no database write lock. | A deliberately stalled endpoint allows evaluation to complete and graceful shutdown to retain both queued transitions. |
| 7 — Clock corrections freeze live measurements | Agents reserve durable report sequence numbers before queueing. Migration 17 stores a server watermark independently of metric retention; it commits with live state. Restored agent counters learn the server watermark without renumbering backlog. Inventory refresh uses monotonic elapsed time. Measurement receipt time is distinct from heartbeat and observed time; stale readings and timestamp offsets are surfaced, and stale resources cannot open or recover notifications. | Forward/backward clock changes, replay, retained-history deletion, server restart, counter restart/loss/recovery, legacy handoff, installation confirmation and real server-to-Chromium live recovery. |
| 8 — Live events remove source data | Agent reports publish the same canonical projection used by GET/bootstrap. The browser tracks events that arrive during a snapshot request without relying on the agent's clock. | Real report/source/snapshot/SSE API test and Chromium test checking that source details remain visible through live reports. |
| 9 — Hanging browser requests stop refresh | API requests have a 20-second deadline covering headers and body, plus caller cancellation. `useInventory` owns SSE, snapshot recovery and coalesced refreshes. Requests queued during a fetch trigger a subsequent fetch. Source history refreshes every 30 seconds and retries after failures; host history periodically reloads even without new reports. | Transport tests for stalled connections, stalled bodies and caller cancellation; Chromium tests for snapshot recovery, authentication retry and source history refresh. |
| 10 — Publishing races agent downloads | Fresh installers embed the selected release ID and key together. Upgrades select once per attempt while saved updaters retain their trust key. Manifest, signature and binary requests use immutable ID-addressed URLs. Publishing retains every replaced release for at least 24 hours, plus the current and recent releases. Flat trees remain readable for legacy clients but cannot offer new installations. | Real signed installer tests publish between all eight download steps and after selection, including key rotation. Server tests cover stable contents, cache policy, namespace confinement and flat-layout refusal. Assembly tests cover rapid publications and expiry after replacement. |

Final verification also exposed an intermittent SQLite lock error when a host save raced SSH progress. Read/modify/write transactions now reserve SQLite's writer with `BEGIN IMMEDIATE` before reading; read-only projections retain ordinary snapshot transactions. This avoids stale-snapshot write upgrades even when an independent single-statement writer does not use the application mutex. A deterministic test holds an independent writer, verifies that a host save waits, and then confirms successful persistence after the writer commits.

Existing saved agent updaters need one manual console upgrade command to adopt immutable downloads. Automatic binary upgrades deliberately preserve their installed updater code and trust key. An already downloaded initial installer remains tied to its original release, including across signing-key rotation; fetch a fresh installer after its release leaves the retention window.

Clock-independent ordering requires both the new server and agent. Once an identity sends ordered reports, older unsequenced binaries cannot advance its live state; update that agent again after a rollback to resume measurements. Legacy agents retain timestamp ordering until upgraded.

The storage migration cannot infer the provenance of addresses already unioned by old versions. Those addresses are conservatively retained. Existing IDs, source histories and aliases remain reachable. The identity refactor does not add retire/forget/purge semantics.

Notification delivery is at least once, so crash recovery can duplicate an accepted message. The queue is bounded at 4,096 entries. Full queues postpone condition changes; new-device announcements at capacity are omitted with a warning. These limits and cancellation semantics are documented in [operations](../operations.md#notifications).

Follow-up reliability work after the baseline findings:

- Linux ARP discovery now reconciles interface changes in the background, reopens sockets after reader or send failures, and exposes current socket availability through API capabilities. A unit test verifies that unchanged interfaces retain their sockets. Physical interface replacement and raw-socket recovery still need validation on a native Linux x86_64 host.
- Scheduled scans pace probe starts at the backend boundary, so executor delays cannot bunch probes after they have been dispatched. The scanner test checks aggregate start spacing while allowing bounded parallel probes.
- The reporting actor now services completed HTTP and child-delivery requests before draining its sample queue. A continuous stream of ready samples could otherwise starve accepted reports because the `select!` was biased toward sample collection. The regression test holds the mock response until a second sample finishes, then verifies that one-off reporting still completes.
- The enrichment queue catches worker panics, logs the affected host, marks enrichment failed, clears its pending marker and continues processing later devices. A regression test simulates a panic and verifies both the visible failure state and that the next item completes.
- Enrollment capacity is checked transactionally against active identities for both fresh enrollment and revoked-identity recovery. Revoked and uninstalled identities preserve history while freeing a slot; concurrent enrollment and reset tests verify the 250-agent ceiling and token retry behavior.
- `/readyz` separates database readiness from process liveness with a one-second SQLite check and immediate shutdown refusal. Authenticated `/api/v1/system/status` reports background-loop progress, notification backlog age and host/source raw-metric retention lag; a new indexed migration keeps source retention diagnostics and cleanup bounded. Delivery success is distinguished from remote acceptance by the durable outbox depth and age.
- The filesystem worker-cap test now gates its worker with channels instead of relying on a short sleep. The clock-order integration test compares SQLite `REAL` timestamps with a microsecond tolerance, avoiding platform-dependent last-bit differences. Other reporting deadlines allow for loaded CI and emulated builds.
- The explicit retention-load fixture now includes populated host telemetry, container history on 25 hosts, source inventory and source metrics, plus concurrent report, discovery-write and host/source history reads. It no longer enforces an unmeasured per-report latency target; `make linux-load-checks` emits the release-mode Linux x86_64 benchmark record.

## Validation

- Linux x86_64 container checks: 279 passed, one intentionally ignored retention load test, including readiness and operational-status tests, Linux ARP reconciliation, enrollment-capacity and enrichment panic recovery tests plus the storage-boundary compile-fail doctest; strict workspace Clippy and Rust formatting pass.
- Native workspace tests: 278 passed and one intentionally ignored retention load test, including readiness and operational-status tests, enrollment-capacity, enrichment panic recovery and storage-boundary compile-fail tests. The Linux-only ARP test runs in the Linux container suite.
- Web production build, TypeScript and ESLint pass.
- Chromium/Playwright: 64 passed, including transport/recovery tests, measurement freshness checks and real-server live/source/clock history tests.
- Release assembly harness: 20 passed.
- Installer harness: 165 run; 152 passed and 13 out-of-scope macOS agent fixtures skipped. The host fixtures now stub the operating system explicitly and run on this macOS development host; 16 activation tests use real SQLite and filesystem operations with only systemd/HTTP stubbed.
- Shell syntax, ShellCheck, generated protocol drift and eight documentation tests pass.

The Rust, installer, release, shell, protocol and documentation checks were rerun for server activation and immutable downloads. Rust, browser, web build/type/lint, shell, protocol and documentation checks were rerun for report ordering. The Linux x86_64 gate built its target and server images under emulation, assembled signed releases, and brought up the server behind Caddy; the private-CA HTTPS setup request succeeded. The install and SSH matrix could not start because the Debian target on this Docker Desktop ARM64 host remains systemd-degraded and cannot start `sshd`. The native updater fixture also refuses this ARM64 host. Native Linux x86_64 service-manager, raw-socket/interface recovery and pmxcfs behavior, actual GitHub publication, populated load and multi-day soak remain unverified.

The expanded retention-load fixture passed in release mode on macOS arm64: 1,154,550 populated host samples and 2,500 source samples, with concurrent report, discovery-write and host/source history-read workers. It measured 1.76 GB of database storage and about 0.9 seconds for retention on that machine. The same fixture passed through `make linux-load-checks` as Linux x86_64 under Docker's arm64-host emulation: retention took about 3 seconds; report latency was 6.5 ms median/56 ms max and paired host/source history reads were 33 ms median/113 ms max. Both sets of numbers are diagnostic only and do not satisfy the native Linux x86_64 populated-load gate.

## Remaining blockers before recommendation

1. **Linux x86_64 acceptance.** Exercise actual packaged artifacts through fresh installation, upgrade, failed activation/restore, restart, interface replacement/raw-socket recovery, notification outage, database/disk pressure, guest churn and browser reconnection. Measure realistic inventory/history load and run a multi-day soak. The locally passing suites do not establish these release gates.

Additional follow-ups from the baseline review remain: deliberate device retirement and purge semantics; realistic populated-load measurements on native Linux x86_64. The 250-agent ceiling now applies atomically to active identities, so revoked or uninstalled identities retain history without consuming an active slot. Discovery interface recovery is implemented, but its behavior on actual Linux x86_64 network changes remains unverified as noted above.

The project is materially more reliable, but the unverified Linux acceptance gates still prevent a recommendation for unattended use.
