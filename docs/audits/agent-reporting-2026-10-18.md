# Agent updates and reporting audit — 18 October 2026

Baseline audited commit: `21d1413`. The initial investigation left production code unchanged; the implementation follow-up below describes subsequent working-tree fixes. This audit covers collection, delivery, installation/update rollback, server validation/history, and the console/notification consumers.

Several independent bugs can explain an apparently running agent that stops reporting. The strongest reproduced cause is collector starvation. Linux CPU collection also has a separate scope error: a systemd installation can report the agent service's CPU consumption as the machine's CPU consumption.

These are repository findings, local reproductions and the later read-only hosted observations below, not a diagnosis from an affected production host's logs. Linux cgroup and real service-manager behavior still need validation on affected machines. The local Docker executable is a broken symlink, so the privileged Linux updater gate could not run. No installed services or external hosts were changed.

## High-priority correctness and availability defects

### 1. P1 — Slow collectors can indefinitely starve report delivery

**Reproduced with the unmodified agent.** In [reporting.rs](../../crates/hope-agent/src/reporting.rs#L106), the biased select checks the sampling deadline before the HTTP future and delivery timer. Its sampling branch awaits the entire collector, then schedules the next deadline from the *start* of that collection. When collection consistently exceeds the interval, the deadline is already due again. The HTTP future can remain unpolled indefinitely while new samples accumulate.

[collect.rs](../../crates/hope-agent/src/collect.rs#L558) runs collectors sequentially: Docker alone permits 2 seconds for `ps` and 5 seconds for `stats`, before gateway, GPU, ZFS, services and monitors. The allowed 5- and 10-second reporting intervals are therefore easy to overrun. Even without permanent starvation, collection blocks HTTP progress and shutdown handling for its duration.

Reproduction: use a local accepting endpoint that returns `report_interval_seconds: 5`; provide a Docker CLI fixture whose `ps` takes 1.5 seconds and whose `stats` hits its existing 5-second timeout. Run `hope-agent run` for 54 seconds. Observed: one report accepted, continued sample collection, no errors, and three reports still queued. The initial scheduling interval is 30 seconds, which is why this does not fail immediately after startup.

**Fix:** isolate sampling from delivery, retain at most one active collection, and skip missed sampling deadlines. Bound collection duration and keep delivery/shutdown independently pollable. Add a test where collection is slower than the requested interval; the existing inverse test only verifies sampling during slow HTTP.

### 2. P1 — Linux CPU can measure only the agent service

**Confirmed by code path; not executed on Linux during this audit.** [read_cgroup_cpu_sample](../../crates/hope-agent/src/collect.rs#L272) reads `/proc/self/cgroup`, then the corresponding cgroup's usage counter. [Metrics construction](../../crates/hope-agent/src/collect.rs#L807) prefers this value over host CPU usage on every Linux machine where it is readable. There is no distinction between a container boundary and a systemd service cgroup.

For a typical systemd agent at `/system.slice/hope-agent.service`, this measures the agent and its children, not other services on the host. A service inside an LXC guest can make the same mistake at a nested service cgroup. An otherwise busy server can consequently look almost idle. Cgroup capacity constraints do not correct the numerator's scope.

**Fix:** explicitly select the monitored machine/container boundary. Use host counters for a host installation and a verified guest boundary for container installations. Report CPU source, scope and effective capacity. Validate with load outside the agent's cgroup, both on a systemd host and inside LXC.

### 3. P1 — A transient HTTP authorization response can permanently stop reporting

**Reproduced.** [delivery.rs](../../crates/hope-agent/src/delivery.rs#L126) treats every HTTP 401 or 403 as credential revocation. [main.rs](../../crates/hope-agent/src/main.rs#L36) deliberately exits successfully for this outcome. Both generated services restart only on unsuccessful exit: [systemd and launchd definitions](../../scripts/install-agent.sh#L717).

A proxy/access-policy 403 therefore produces one request and exit code 0. Restoring access does not restart the agent. This can also occur during an update or rollback if the first response is a transient denial. Intentional revocation should still stop the agent; an arbitrary HTTP status does not authenticate that meaning.

**Fix:** distinguish the server's structured, definitive revocation response from generic HTTP denial; retry ambiguous authorization failures with bounded backoff. Preserve intentional revocation semantics and expose the actual failure category.

### 4. P1 — One optional metric can invalidate every host report

**Reproduced against the real server.** [Docker collection](../../crates/hope-agent/src/collect.rs#L105) forwards unbounded string fields. [Server validation](../../crates/hope-server/src/validation.rs#L164) restricts `ports` to 512 bytes, among other limits. A normal container with many published ports produced 698 bytes and HTTP 400 `Invalid containers`.

Validation is all-or-nothing in [agents.rs](../../crates/hope-server/src/agents.rs#L359). The agent [drops a rejected sample](../../crates/hope-agent/src/reporting.rs#L140), logs only its status code, then repeats with the same offending data. CPU, memory, storage and heartbeat updates all disappear because of optional Docker metadata. A new release adding such a collector may fail first-report confirmation; a later environmental change can break reporting after installation was already committed. Filesystem/inventory strings and total payload size have similar collector/server-contract risks.

**Fix:** enforce a shared collector/protocol contract before queuing. Isolate invalid optional readings, mark that collector degraded, and keep core reporting alive. Preserve a bounded server rejection reason in diagnostics. Test realistic long port lists and maximum payload sizes.

### 5. P1 — Hard-interruption recovery depends on an updater that may never run again

**Reproduced in the installer harness; real systemd/launchd recovery remains unverified.** The updater [deletes the request before acquiring its lock](../../scripts/install-agent.sh#L229). An orphaned lock under 30 minutes old makes it return success without processing the request. A transaction left after the agent was stopped is only repaired when the installer is invoked again: [recovery](../../scripts/install-agent.sh#L461).

The harness confirmed both ingredients: SIGKILL after `stop` leaves no active agent and a transaction; a retry with a fresh orphaned lock deletes the request, retains the lock and exits 0 with “another update is already running.” Combined with a stopped agent, there is nobody to enqueue another request. On Linux, an installer-only SIGKILL can be retried by the current updater unit because it exits 137; the orphaned-lock case additionally requires interruption of the wrapper/cleanup. Ordinary handled failures do have rollback coverage.

**Fix:** use a process-owned lock, consume requests only after ownership is acquired, and make interrupted-transaction recovery independent of future agent reports. Cover killing the entire updater process group, not just the installer child, with a real service manager.

### 6. P1 — Missing telemetry can be announced as recovery

[Collection](../../crates/hope-agent/src/collect.rs#L647) emits empty metric lists when storage, services or pools cannot be read. [Notification evaluation](../../crates/hope-server/src/notify.rs#L263) stops producing the corresponding problems; [recovery handling](../../crates/hope-server/src/notify.rs#L468) deletes every alert absent from the current problem set and may send “This problem has cleared.” Collector availability is not considered.

A filesystem timeout, unavailable `zpool`, or failed `systemctl` can therefore resolve a full-disk/degraded-pool/failed-service alert without a healthy observation. Going entirely silent also removes resource problems while opening the separate agent-offline problem. The console's inventory fallback can still show the old full disk while the notification path declares recovery.

**Fix:** model healthy, unhealthy and unknown separately. Require a fresh successful observation to resolve resource alerts; mark telemetry loss explicitly.

## CPU timing and update lifecycle defects

### 7. P2 — CPU source switches after startup, and its elapsed time is wrong

[CPU construction](../../crates/hope-agent/src/collect.rs#L807) skips the cgroup probe entirely on the first sample. The second sample seeds its baseline and falls back to sysinfo. The third starts reporting cgroup usage. Every restart can therefore look like “missing CPU → host CPU → agent-cgroup CPU.” The first missing reading is deliberate warmup; the subsequent scope switch is erroneous.

Separately, [elapsed time](../../crates/hope-agent/src/collect.rs#L559) is measured between collection starts, but cgroup usage is read after all other collectors. Variable Docker/ZFS/monitor latency changes the actual counter interval. Disk and pool counters taken later in collection share this timing problem. Clamping CPU to 100% hides inflated measurements.

**Fix:** prime the selected source on sample one; keep a monotonic timestamp with each counter baseline, read close to that timestamp, and emit unavailable on source/capacity changes rather than silently mixing sources.

### 8. P2 — Binary updates do not update the updater, and the usual upgrade command cannot repair a current installation

The [pinned installer](../../scripts/install-agent.sh#L211), wrapper and updater units are retained across automatic binary updates (`HOPE_UPDATER=1`; [completion](../../scripts/install-agent.sh#L840)). This preserves their historical bugs even after a newer agent is installed. For example, commit `0508a2a` added transient-failure restart behavior in the generated unit; a binary-only update does not install it.

The [console upgrade command](../../crates/hope-server/src/agents.rs#L77) passes `HOPE_ONLY_NEWER=1`. When the binary is already current, [the installer exits early](../../scripts/install-agent.sh#L590), before updater setup. Thus the apparent repair command does not refresh a stale updater on a current agent.

History also documents an older rollback/retry loop fixed in agent commit `c51dccf`: rollback restarted the old process, which immediately requested the failing release again. Old deployed agents may still have that behavior; the current source persists `update-asked` to throttle it.

**Fix:** version and migrate updater components separately from the agent, keeping the pinned trust key separate from implementation. Provide a repair path that runs even when the binary is current. Validate an actual old-installed-updater → current-release migration.

### 9. P2 — macOS records successful updates as failed

**Reproduced natively and through the macOS harness.** [Outcome parsing](../../scripts/install-agent.sh#L264) uses BRE alternation `\(updated\|current\)`, which macOS's native `sed` did not match. The installer printed `result=updated v2`, the new binary was installed, and the wrapper exited 0, but `update-result` contained `status=failed` and `code=UNKNOWN`.

The native 104-test installer run failed the three existing tests that inspect successful/current outcomes. The macOS-specific update test passes because it only checks the installed version. This audit did not execute a real launchd update.

**Fix:** use a portable parser or `sed -E` with ERE grouping/alternation; verify structured outcomes on both platforms.

### 10. P2 — A backward clock correction freezes live CPU and inventory

**Reproduced against the real server.** [Timestamp validation](../../crates/hope-server/src/agents.rs#L349) accepts up to five minutes of future skew. [Live-state ordering](../../crates/hope-server/src/agents.rs#L417) then refuses to replace any reading older than that accepted timestamp. A sample 240 seconds ahead at 99% followed by a current 10% sample returned success, while live CPU stayed at 99%.

`last_report` still advances, so the UI can say the agent is reporting while showing the frozen value. The local [acceptance-marker ordering](../../crates/hope-agent/src/reporting.rs#L130) also depends on wall-clock ordering; a backward step can hold markers back and interfere with update confirmation.

**Fix:** give reports a boot/run identity and increasing sequence, retain collection and receipt time separately, and explicitly handle clock corrections. Keep timestamp validation without letting an accepted future timestamp monopolize live state.

### 11. P2 — Update status omits the state needed to diagnose failures

[Updater availability](../../crates/hope-agent/src/updates.rs#L105) means only that the queue directory exists, including when installing/enabling the actual updater failed. Permission errors while enqueuing and persisting retry state are ignored. [Result descriptions](../../crates/hope-agent/src/updates.rs#L126) discard the stored `at` timestamp and failed target/attempt identity.

The server keeps a request pending for a day; the agent suppresses repeated requests for the same version for an hour. [The UI](../../web/lib/fleet.ts#L428) can therefore show “pending” after failure or while a deliberately repeated click cannot produce another attempt. The failed release is also retried hourly while the request remains pending, including deterministic failures.

**Fix:** report attempt ID, target, updater version, phase, timestamps, retry time and terminal outcome. Distinguish unavailable, queued, downloading, restarting, verifying, rolled back and failed. Make explicit retry distinct from automatic retry.

The following are absent or incomplete in [Inventory/Metrics](../../crates/hope-protocol/src/lib.rs#L323). These are proposed scope priorities, not claims that every feature was promised for this release.

## Inefficiencies and resilience weaknesses

- **Four durable state writes per normal accepted sample.** [Reporting](../../crates/hope-agent/src/reporting.rs#L116) writes the spool before sending, writes `last-report`, writes `last-acceptance.json`, then rewrites the spool. [Each write](../../crates/hope-agent/src/config.rs#L82) fsyncs both file and parent directory. At five-second reporting this is about 69,120 file replacements and 138,240 explicit sync calls per agent per day. It also serializes the whole backlog during outages. Retain crash safety while coalescing redundant state/markers and measuring the flash/storage cost.
- **Repeated serialization to enforce spool size.** [Spool trimming](../../crates/hope-agent/src/delivery.rs#L87) encodes the entire queue, potentially repeatedly while evicting. Track serialized size or use bounded append/checkpoint storage; report evictions rather than silently losing old samples.
- **Collectors repeat expensive work every sample.** Docker starts two CLI processes, services enumerate all units, filesystem inventory is reconstructed, and `/proc/diskstats` plus `/sys/block` checks are read twice. ZFS can read up to 4,096 objsets for each of 64 pools without an overall deadline. Cache slow-changing inventory/capabilities, share one counter snapshot, independently schedule expensive collectors and cap total work.
- **Some supposedly bounded collection still blocks the runtime.** `refresh_cpu_usage`, memory/sensor refresh and [root `statvfs`](../../crates/hope-agent/src/collect.rs#L576) are synchronous on the current-thread runtime; root filesystem fallback is outside the detached disk worker. A blocked kernel/filesystem call cannot be rescued by the collector's existing timeout. Isolate potentially blocking I/O, with bounded worker count and explicit unknown/freshness state.
- **Release publication is atomic per HTTP request, not per update session.** [Release resolution](../../crates/hope-server/src/releases.rs#L38) follows `current` for every request, while [the installer](../../scripts/install-agent.sh#L536) makes four HEAD requests and separate manifest/signature/artifact downloads. Publication between requests can mix releases and cause safe but avoidable signature/hash failures before service stop. Use immutable versioned/digest URLs or retry against one pinned release. The request file's target is intentionally ignored by the updater, so the installed release can also differ from the requested target if publication changes.
- **macOS error logs have no rotation configured by this installer.** Repeated invalid reports write to `agent.log` indefinitely. Add bounded rotation or use a managed logging sink.

## Suggested repair order and acceptance tests

1. Fix scheduler fairness/collector isolation and prove reports continue with a collector slower than 5 seconds. Include shutdown and HTTP timeout behavior.
2. Fix Linux CPU scope/timestamps and compare against independent host/guest counters under controlled load outside the agent cgroup, including nested LXC/systemd and quota changes.
3. Separate authoritative revocation from transient denial; isolate invalid optional telemetry. Exercise 403 recovery, long Docker ports, duplicate monitors and maximum-sized inventories.
4. Repair updater lifecycle/migration, portable parsing and orphan recovery. Run real systemd and launchd update/rollback matrices, including full process-group interruption and migration from an older pinned updater.
5. Add unknown/freshness states before expanding collector coverage. Test that unavailable collectors cannot generate recovery notifications and that clock changes cannot freeze current values.
6. Add reboot/self-health, storage health/inodes, NIC errors and CPU breakdown, then service/container state and sustained alerts. Measure normal and outage resource use after changing collection and durable writes.

## Crate research follow-up

The [crate evaluation](agent-crates-2026-10-18.md) maps maintained library candidates to these findings, including versions, compatibility, dependency tradeoffs and sources. Priorities are to use more of the existing `sysinfo`/Tokio APIs, replace Linux parsers with `procfs-core`/`procfs`, replace Docker CLI parsing with `bollard`, and evaluate a compatible zbus stack for systemd. It also covers cgroups, filesystem/watchdog helpers, GPU reporting, version comparison and updater libraries. None of these substitutes for fixing measurement scope, scheduler fairness or transaction recovery.
