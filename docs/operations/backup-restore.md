# Backup and clean restore

This procedure protects all state required to restore Hope, not only
PostgreSQL. Test it on a separate Compose project before relying on it for
recovery. The current deployment has no automatic backup, WAL archiving,
point-in-time recovery, or backup encryption.

The repository also contains `deploy/compose/backup.sh` and
`deploy/compose/restore.sh` convenience wrappers. `backup.sh` refuses to run
unless `HOPE_BACKUP_INCLUDE_SECRETS=1` is set. `restore.sh` is an in-place,
destructive restore and requires `--force`; use the separate Compose project
procedure below when validating a backup without replacing the current
deployment. The wrapper stores the deployment env as `deployment.env` and uses
the configured host paths for the credential key and release repository.

## What to back up

Keep these items together in one access-controlled backup set:

- PostgreSQL logical dump. It contains users, sessions, inventory, jobs,
  credentials ciphertext, agents, maintenance events, and update state.
- `deploy/compose/secrets/credential-master-key`. This 32-byte key is required
  to decrypt credential ciphertext after a database restore.
- The `server-pki` volume. It contains the CA certificate and private key plus
  the server certificate and private key generated by `server ca init`.
- The read-only `deploy/compose/agent-releases` repository, including signed
  bundles and `public-key.hex`.
- The deployment `.env`, stored as a secret. It carries database connection
  settings, trust-file paths, retention settings, and any release key-rotation
  value.
- The release signing private key, if this operator signs releases. Store it
  separately in an offline secret-management system. Never mount it into the
  server or worker and never place it in `agent-releases`.

The public key in `agent-releases/public-key.hex` is release verification trust,
not the private signing key. If a rotation uses `HOPE_RELEASE_PUBLIC_KEYS`, back
up the exact old/new key list with `.env`.

The wrapper uses `HOPE_DEPLOYMENT_ENV_FILE` when set, otherwise the repository
`.env`. It uses `HOPE_CREDENTIAL_MASTER_KEY_FILE_HOST` and
`HOPE_AGENT_RELEASE_DIR_HOST` for non-default host paths. These are host-side
backup settings; the container still reads the mounted key at
`/run/secrets/hope_credential_master_key`.

## Create a backup

Run from the repository root. Stop API and worker writes first; keep
PostgreSQL running for the logical dump. Commands use `sha256sum`; on macOS,
install GNU coreutils or replace it with an equivalent SHA-256 manifest and
check command.

```sh
BACKUP_DIR="$(pwd)/backups/$(date -u +%Y%m%dT%H%M%SZ)"
umask 077
mkdir -p "$BACKUP_DIR"

docker compose -f deploy/compose/docker-compose.yml --env-file .env stop server worker

docker compose -f deploy/compose/docker-compose.yml --env-file .env \
  exec -T postgres sh -c \
  'pg_dump --format=custom --no-owner -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  > "$BACKUP_DIR/postgres.dump"

cp deploy/compose/secrets/credential-master-key \
  "$BACKUP_DIR/credential-master-key"
cp .env "$BACKUP_DIR/deployment.env"

docker compose -f deploy/compose/docker-compose.yml --env-file .env \
  run --rm --no-deps -v "$BACKUP_DIR:/backup" server \
  sh -c 'tar -C /app/data/pki -czf /backup/server-pki.tar.gz .'

tar -C deploy/compose -czf "$BACKUP_DIR/agent-releases.tar.gz" agent-releases

( cd "$BACKUP_DIR" && \
  sha256sum postgres.dump credential-master-key deployment.env \
    server-pki.tar.gz agent-releases.tar.gz > SHA256SUMS )

docker compose -f deploy/compose/docker-compose.yml --env-file .env up -d
```

Protect the backup directory like the database password and credential key.
Copy the signing private key to its offline backup location separately. Verify
the set before moving it off the host:

```sh
( cd "$BACKUP_DIR" && sha256sum -c SHA256SUMS )
```

The Compose volumes are not backups. `docker compose down` preserves them;
`docker compose down -v` removes `postgres-data` and `server-pki`.

## Clean restore

Use a new Compose project name. This keeps the old containers and volumes
available until the restore passes its checks. The example assumes the backup
contains the `.env` used by the original deployment.

```sh
BACKUP_DIR="$(pwd)/backups/20260920T120000Z"
RESTORE_PROJECT=hope-restore

( cd "$BACKUP_DIR" && sha256sum -c SHA256SUMS )

cp "$BACKUP_DIR/deployment.env" .env
mkdir -p deploy/compose/secrets
install -m 0400 "$BACKUP_DIR/credential-master-key" \
  deploy/compose/secrets/credential-master-key
```

Restore the release repository before starting application services. Move an
existing directory aside instead of merging files from two deployments:

```sh
mv deploy/compose/agent-releases \
  "deploy/compose/agent-releases.before-${RESTORE_PROJECT}"
mkdir -p deploy/compose
tar -C deploy/compose -xzf "$BACKUP_DIR/agent-releases.tar.gz"
```

Start only a new PostgreSQL service and wait for its health check:

```sh
docker compose -p "$RESTORE_PROJECT" \
  -f deploy/compose/docker-compose.yml --env-file .env up -d postgres
docker compose -p "$RESTORE_PROJECT" \
  -f deploy/compose/docker-compose.yml --env-file .env ps postgres
```

Restore the logical dump into the fresh database. Replace `hope` values if the
backup used different `POSTGRES_USER` or `POSTGRES_DB` values.

```sh
docker compose -p "$RESTORE_PROJECT" \
  -f deploy/compose/docker-compose.yml --env-file .env exec -T postgres \
  sh -c 'pg_restore --clean --if-exists --exit-on-error --no-owner \
    -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < "$BACKUP_DIR/postgres.dump"
```

Restore the exact PKI files into the new named volume before starting `server`:

```sh
docker compose -p "$RESTORE_PROJECT" \
  -f deploy/compose/docker-compose.yml --env-file .env \
  run --rm --no-deps -v "$BACKUP_DIR:/backup:ro" server \
  sh -c 'mkdir -p /app/data/pki && tar -C /app/data/pki -xzf /backup/server-pki.tar.gz'
```

Start server first, then worker. The server applies any migrations newer than
the dump; the worker also runs the embedded migration runner when it starts.

```sh
docker compose -p "$RESTORE_PROJECT" \
  -f deploy/compose/docker-compose.yml --env-file .env up -d server
curl -fsS http://127.0.0.1:8080/health/live
curl -fsS http://127.0.0.1:8080/health/ready

docker compose -p "$RESTORE_PROJECT" \
  -f deploy/compose/docker-compose.yml --env-file .env up -d worker
docker compose -p "$RESTORE_PROJECT" \
  -f deploy/compose/docker-compose.yml --env-file .env ps
```

Check all of the following before switching traffic:

1. The readiness endpoint returns `{"status":"ready"}`.
2. Login works with the restored operator account.
3. Worker logs show `worker started` and no missing-key or migration error.
4. A credential-backed operation can decrypt its selected credential.
5. The release API sees the restored repository and accepts a known signed
   bundle without publishing an update.
6. An existing agent reconnects with its original state directory, or the
   operator has scheduled re-enrollment for that agent.

Keep the old project stopped but intact until these checks pass. If the restore
must replace the old deployment, stop both projects, update the reverse proxy
and agent endpoint routing, then remove old volumes only after a retention
decision. Do not run `down -v` as a first response to a failed restore.

## Missing key material

Restore exact bytes. Do not generate replacements during incident recovery.

| Missing material | Consequence | Recovery boundary |
| --- | --- | --- |
| PostgreSQL dump or volume | Durable control-plane state is unavailable. | Restore the database or accept a new deployment with no prior state. |
| Credential master key | Credential ciphertext remains present but cannot be decrypted. Credential-backed install, repair, and update work fails. | Restore the exact key. Replacing it does not decrypt old rows. |
| CA key/certificate or server key/certificate | Agent gateway and enrollment cannot preserve their configured identity. | Restore the exact `server-pki` contents. A new CA has a new fingerprint and requires re-enrollment of every agent. |
| `agent-releases/public-key.hex` or configured public-key list | Release manifests and artifacts fail trust verification. Automatic and explicit agent updates stop; already-running agents continue their current binary. | Restore the exact trust list and signed bundles. A missing signing private key prevents new releases under that key but does not invalidate existing signed bundles. |
| An agent's private key, client certificate, or CA certificate | That agent cannot authenticate or verify the gateway. | Re-enroll that host through a new single-use token. Never copy another host's private key. |

Restoring the CA certificate without its matching private key is not a usable
partial restore. Do not run `ca init` against a deployment that lost its CA and
then expect enrolled agents to trust it; the new CA is a different identity.
