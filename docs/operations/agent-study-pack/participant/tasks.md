# Agent workflow tasks

Thank you for trying these workflows. We are testing the interface, not you. Work as you normally would; uncertainty, wrong turns and stopping are useful observations.

Use the application and hosts named on your session sheet. Start each task from the Agents page. Do not read the next task early. Before your first click or scroll, record what the page tells you and what you expected to see. Then use the app freely.

Start a timer when you begin each task. Stop it when you think you have finished or when five minutes have passed. Background installation or update waiting may exceed this: record active time and waiting time separately. If you need help, record the help and continue only if the study owner says it is safe. Do not guess which machine or release to use.

Do not paste passwords, enrollment commands, tokens or private log content into your response. Screenshots are optional; remove secrets first.

## Task 1 — Bring a new host online

Install an agent on the disposable target named on your sheet. Decide when it is ready to use. Explain what makes you confident that this particular host is sending useful data, and whether anything remains to be done.

Record your response before starting task 2.

## Task 2 — Explain old readings

Investigate the existing host named for task 2. Its readings appear old. Explain what is happening, what evidence supports your explanation, and what you would do next. Do not change the host's network or permissions yourself.

## Task 3 — Investigate a resource spike

Investigate the host and time period named for task 3. Find the resource spike and any log evidence that helps explain it. Record the time you investigated and your conclusion. Take enough time to read the relevant entries even while new data is arriving.

## Task 4 — Control a noisy source

For the source named for task 4, keep warnings and more severe messages and apply a limit of five records per minute. Decide when the host is using your change. Explain what happens to messages that do not reach the server and how you would tell whether information was lost.

## Task 5 — Interpret an unsuccessful update

Request the test release named for task 5 on the specified host. The study environment includes an unsuccessful update scenario. Explain the eventual outcome, which version is running, and whether useful data is arriving. Distinguish an operation still in progress from a completed outcome.

## Final reflection

Which page required the most searching? What did you expect to see immediately? Which label or state was least clear? What single change would make these tasks easier?
